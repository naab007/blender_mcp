# v2.3.0

Phase D1: the generic driver. 13 tools that address Blender's RNA and operator layer
directly, CDP-style, instead of one hand-written tool per question, plus the additive
rides-along on existing tools. 182 tools (169 + 13; `tests/baseline_tools_2.3.txt` cut at the
D-G3 test gate). Contract: docs/PLAN.md section 12 (D1.3, G1-G19) and docs/LEAD-RULINGS-C.md
(R1-R38). Wire protocol stays 1: every 2.2.0 tool keeps its name, position and schema
(additive parameters only).

### New tools (section 35 of TOOLS.md)
- `describe`: any struct, property or operator from Blender's own definitions (`bl_rna`):
  types, subtypes, units, ranges, enum items, read-only flags, functions, `poll_now` for
  operators, `what="ops"` + `search` to list operators. Descriptions are the first thing the
  reply cap drops, whole properties the last; `count` kept vs `total`.
- `rna_get` / `rna_set`: any property by ref, many refs per round trip; values coerced and
  validated against the RNA definition (enum membership, range, type, read-only); teaching
  errors with `valid`, `closest`, `tried` and Blender's own text under `rna_error`.
- `find` / `context_info`: query IDs by type, name glob and `where` conditions (uids back);
  the context an operator will see, including `background`.
- `data_new` / `data_remove`: `bpy.data.<collection>.new(...)` with linking and initial sets;
  removal with `do_unlink` / `purge_orphans`.
- `call_operator` / `call_method`: any `bpy.ops` under a declared context (mode, active,
  selected, area / region, a whitelisted `extra`), parameters validated before the poll; any
  RNA function (`from_pydata`, `evaluated_get`, `to_mesh`, `new_from_object`).
- `scene_snapshot` / `scene_diff`: capture IDs by uid, diff two snapshots or a snapshot
  against NOW: `added`, `removed`, `renamed` (by uid), `changed`.
- `batch` / `transaction`: many commands in one round trip with `"$id.path"` references and
  undo on failure; `BEGIN` / `COMMIT` / `ROLLBACK` as one undo step (Scene marker `_mcp_txn`).
- Refs: `#<uid>`, `IDTYPE:Name`, `<ref>/rna.path`, `context/...`, `data/...`, `prefs/...`.
  Angles are RADIANS by default (`angles="DEGREES"` converts both ways); the hand-written
  tools stay in degrees.
- Two server settings: `driver_reply_max_chars` (24000, env `BLENDER_DRIVER_REPLY_MAX`) and
  `driver_batch_max` (200, env `BLENDER_DRIVER_BATCH_MAX`); the server sends the cap on every
  read and refuses an oversized batch without contacting Blender.

### Existing tools (additive)
- `uid` on every object entry of `get_scene_info`, `get_object_info`, `find_objects_by_type`,
  `get_armature_info`.
- `execute_blender_code(code, result_expr=None)`: `value` for the expression; an exception
  returns `{error: "<type>: <msg>", traceback: [last 3 frames], line}` instead of raising.
- `get_version` (add-on reply): `registries: {name: count}` over every `blendermcp_*`
  registry in `bpy.app.driver_namespace`.
- `add_modifier.params` through the driver's coercer: dotted keys reach nested settings,
  pointer properties accept `#uid`, `IDTYPE:Name` or a plain object name, and an OUT-OF-RANGE
  value is now refused with `outside [min, max]` under `unset` where 2.2.0 silently clamped
  it. The `set` / `unset` reply shape is unchanged.
- `transaction` and `batch(undo=AUTO)` keep one Scene ID property (`_mcp_txn` / `_mcp_batch`)
  while open and mark the file dirty; `COMMIT` / `ROLLBACK` / the end of the batch remove it.
- `get_server_settings` / `set_server_settings` list the two new keys.

### Fixes
- A JSON string value (`'"x"'`) passed to a list-or-object parameter was echoed back as the
  reply with no `Error:` prefix and no wire call, because the shared parser returned a str for
  both a decoded string and its error text. Fixed once in `_parse_json_any` (a decoded
  scalar is `Error: <name> must be a JSON object or list`); the 2.2.0 rigging and animation
  wrappers (`add_bones`, `set_vertex_weights`, `set_pose`, `set_keyframes`) carried the same
  defect and inherit the fix.

### Facts measured on both installs that shaped the design (docs/apichecks/out_*.jsonl)
- Undo WORKS in `--background` Blender on 4.3.2 and 5.2.1, so `transaction` rollback and
  `batch(undo=AUTO)` are asserted for real by the harness, not by a teaching message.
- Scene ID properties do not survive undo (WindowManager ones do), which is why the rollback
  marker lives on the Scene; Blender exposes no undo-stack index.
- `temp_override` accepts any key silently, hence the 16-key whitelist for `context.extra`.
- Headless Blender under `--factory-startup` has a window, a screen and 4 areas: the
  "needs a GUI" error is keyed on `bpy.app.background`, never on the window being None.
- `bl_options` is unreachable for C operators: dropped from `describe(operator)`.
- Uids are monotonic, never reused, survive rename and undo; a full `bpy.data` scan costs
  0.27 ms worst case on 2000 objects, so there is no uid cache.
- `scene.tool_settings.uv_sculpt` is an uninitialised `Paint` in the 4.3.2 factory file and
  its getters crash the process: members of `ToolSettings`, `Paint` and `CurveMapping` are
  never dereferenced (reported as `{struct, path}` and named in `truncated`).
- RNA and operator error texts are identical on 4.3.2 and 5.2.1 and are passed through
  verbatim under `rna_error`.

### Known limits
- `msgbus` delivery cannot be proven headless (`rna_set(publish=True)` stays, nothing asserts
  it); it works in a GUI session.
- Embedded IDs (a material's node tree, shape keys) are reachable by path only, never by
  `#uid`, and are marked `embedded: true`.
- Events (`events_subscribe` / `events_poll` / `events_unsubscribe`, Tier 2) are deferred to
  2.4.0 (R38): the `property` kind would ship untested and the `@persistent` handlers are
  add-on lifecycle risk at the end of a phase. Depsgraph and frame events do fire headless
  and are the testable path for 2.4.0.
- `INVOKE_*` execution contexts need a GUI session and `context.area`; headless they are
  refused before the call.
- The 60 s batch wall cap is checked between commands, never inside one: a single long
  command is never interrupted. On a wall stop the reply is `success: false`, `stopped_at` is
  the first command not run, the rest are `skipped`, `rolled_back` follows the undo mode and
  `error` reads `wall cap <N> s reached after command <i>; <k> skipped`.
- `preferences.addon_disable` is refused only when `module` names this add-on; the other
  refused operators are listed in TOOLS.md section 35.
- Tier 3 (schema dump, generated client, code-to-driver translator, push events) is not
  planned.
